# ORION Phases 2–3 Implementation Plan

> **For agentic workers:** This plan is **not** for autonomous execution. The
> project author writes the implementation code by hand as a learning exercise;
> Claude supplies the tests and reviews the result. Do not implement these tasks
> with a subagent unless the author explicitly asks for that.

**Goal:** Build the permission scope gate and the credibility tracker — two of
ORION's four mechanisms — as small, pure, separately tested modules.

**Architecture:** `scope.py` flattens the alert into `path → value` and refuses a
tool call whose arguments contain the value of any field outside the tool's
declared scope. `credibility.py` holds a moving-average score per tool, with a
floor, and persists it to JSON. Neither module knows the other exists, and
neither touches the Anthropic SDK: Phase 4 wraps both around each tool.

**Tech Stack:** Python 3.11 standard library only (`re`, `json`, `os`,
`pathlib`). pytest.

**Spec:** `docs/superpowers/specs/2026-09-16-orion-alert-triage-design.md` —
read the *Scope gate* and *Credibility tracker* sections first. The scope gate's
matching rules are defined there, with the reasoning for each.

**Prerequisite:** Phase 1 complete — `src/registry.py` with `ToolSpec` exists.

```python
"""Tests for the permission scope gate.

The gate matches on argument *values*, not argument names: the model chooses
what to put in each argument, so a national ID is a leak whether it arrives in
a field called ``name``, ``query`` or anything else.

Specs are built locally rather than taken from ``build_registry()`` so these
tests pin the gate's behaviour, not any one tool's current scope.
"""

from __future__ import annotations

from typing import Any

from registry import ToolSpec
from scope import flatten


def spec_allowing(*fields: str, name: str = "adverse_media_search") -> ToolSpec:
    """Build a spec whose only interesting property is its scope."""
    return ToolSpec(
        name=name,
        description="scope test stand-in",
        input_schema={"type": "object", "properties": {}, "required": []},
        run=lambda **_kwargs: {},
        allowed_fields=frozenset(fields),
    )


MEDIA_SCOPE = ("customer.name", "customer.country")


def test_flatten_produces_dotted_paths_to_leaf_values(alert: dict[str, Any]) -> None:
    flat = flatten(alert)

    assert flat["customer.national_id"] == "CZ-760415-2231"
    assert flat["counterparty.country"] == "EE"
    assert flat["alert_id"] == "ALRT-2026-0917"


def test_flatten_turns_every_leaf_into_a_string(alert: dict[str, Any]) -> None:
    """The gate compares text, so a number must become text first."""
    assert flatten(alert)["transaction.amount_usd"] == "48750.0"


def test_flatten_keeps_only_leaves(alert: dict[str, Any]) -> None:
    """``customer`` is a container, not a value anyone could leak."""
    flat = flatten(alert)

    assert "customer" not in flat
    assert "transaction" not in flat
```

In `src/scope.py`:

`flatten(alert, prefix="")` returns a flat dict whose keys are dotted paths to
every **leaf** value, and whose values are those leaves converted to `str`.

```
{"customer": {"name": "Marek Dvorak"}, "alert_id": "ALRT-1"}
→ {"customer.name": "Marek Dvorak", "alert_id": "ALRT-1"}
```

Hints, not code:
- The alert nests, so the natural shape is recursion: when a value is itself a
  mapping, flatten it with a longer prefix and merge the result in.
- Test for a mapping with `isinstance(value, Mapping)` (from `collections.abc`)
  rather than `dict` — it accepts any mapping type, not just the built-in one.
- Why convert to `str` here rather than later? Because every rule in Task 11
  compares text, and doing it once at the edge means nothing downstream has to
  wonder what type it has.

Two things in `src/scope.py`.

**`ScopeViolation`.** Subclass `Exception`. Store `tool` and `fields` as
attributes, and pass a message to `super().__init__` that names the tool and
every field, for example `adverse_media_search may not receive:
customer.national_id`. That message is what the model reads in Phase 4, so it
has to tell the model exactly what to drop.

**`check_scope`.** Write the **simplest thing that passes these five tests**,
and nothing more:

1. Flatten the alert.
2. The restricted fields are every path not in `spec.allowed_fields`.
3. If any argument value *equals* a restricted field's value, collect that path.
4. If you collected any, raise `ScopeViolation` with them sorted.

Plain equality, top-level arguments only. It is deliberately naive — Task 11's
tests will show you exactly where it falls short, and that is the point of
writing it this way. Resist fixing problems no test has shown you yet.

- [ ] **Step 3: Write the implementation — yours to write**

The rules, from the spec:

1. **Normalize before comparing.** Lowercase, then drop every character that is
   not a letter or a digit. `CZ-760415-2231` and `cz 760415 2231` both become
   `cz7604152231`. One call to `re.sub` does it.
2. **Look inside structures.** An argument can be a list or a dict holding
   strings. Collect every string at any depth. A generator using `yield from`
   is the tidy way to walk it; plain recursion into a list works too.
3. **Short values match whole arguments only.** A restricted value shorter than
   `MIN_SUBSTRING_LENGTH` (after normalizing) matches only when an argument
   equals it. Longer values match anywhere inside an argument.
4. **Shared values are permitted.** If a restricted value is also the value of
   an allowed field, skip it.
5. **Empty values never match.** Skip a restricted value that normalizes to an
   empty string.

Rules 4 and 5 are cheapest to apply once, when you build the set of restricted
values, rather than inside the loop over arguments.

Then add a `# ponytail:` comment where the matching happens, naming the known
ceiling: an encoded or partial value — a base64-encoded ID, just the last four
digits — will not match. Write down the limit you chose, so nobody mistakes it
for an oversight.

- [ ] **Step 1: Write the failing tests**

`tests/test_credibility.py`:

```python
"""Tests for credibility scoring.

The update rule is an exponential moving average with a floor:
``score = max(FLOOR, (1 - ALPHA) * score + ALPHA * outcome)``, where outcome
is 1.0 for success and 0.0 for failure. The expected numbers below are that
formula worked by hand, so each one pins the constants as well as the logic.
"""

from __future__ import annotations

import pytest
from credibility import FLOOR, update


def test_a_success_at_full_trust_stays_at_full_trust() -> None:
    assert update(1.0, success=True) == pytest.approx(1.0)


def test_a_failure_at_full_trust_costs_a_fifth() -> None:
    """0.8 * 1.0 + 0.2 * 0.0 = 0.8"""
    assert update(1.0, success=False) == pytest.approx(0.8)


def test_a_success_recovers_part_of_the_loss() -> None:
    """0.8 * 0.8 + 0.2 * 1.0 = 0.84 -- not all the way back."""
    assert update(0.8, success=True) == pytest.approx(0.84)


def test_repeated_failures_stop_at_the_floor() -> None:
    score = 1.0
    for _ in range(50):
        score = update(score, success=False)

    assert score == pytest.approx(FLOOR)


def test_the_floor_applies_within_a_single_step() -> None:
    """0.8 * 0.11 = 0.088, which is below the floor, so the floor wins."""
    assert update(0.11, success=False) == pytest.approx(0.1)


def test_a_tool_at_the_floor_can_recover() -> None:
    """0.8 * 0.1 + 0.2 * 1.0 = 0.28 -- recoverable distrust, not a death sentence."""
    assert update(0.1, success=True) == pytest.approx(0.28)


def test_the_score_never_exceeds_full_trust() -> None:
    score = FLOOR
    for _ in range(200):
        score = update(score, success=True)
        assert score <= 1.0

    assert score == pytest.approx(1.0)
```

  you are given; `test_the_store_does_not_share_the_dict_it_was_given` fails if

Use `update` rather than repeating the formula. If the rule ever changes, it
should change in one place — and Task 12's tests already prove `update` right.

- [ ] **Step 3: Write the implementation — yours to write**

**`load`** is a `@classmethod`: it builds a store, so it belongs to the class,
not an instance.
- File missing → return an empty store. The first run has no history.
- File present → parse it with `json.loads` and build a store from the dict.
- File corrupt → **do nothing special.** `json.loads` raises
  `json.JSONDecodeError`, which is a subclass of `ValueError`, which is what the
  test expects. The correct amount of error handling here is none: catching it
  and returning a fresh store is exactly the silent reset the test forbids.

**`save`** writes the scores as JSON. Two requirements the tests cannot see:

- **Write atomically.** Write to a temporary file next to the target, then
  `os.replace` it onto the real path. If the process dies halfway through a
  plain write, the file is left truncated — and by the rule you just
  implemented in `load`, a truncated file is an error on the next run. An
  atomic replace means the file is always either the old version or the new
  one, never half of each.
- **Sort the keys and indent.** A reviewer opening this file should be able to
  read it, and diff two runs of it.
